## 1. 背景与目标

### 1.1 产品定位

**YAML 流程模板 + 执行引擎**

核心能力：
- 开发者预置 YAML 流程模板，用户开箱即用
- 执行引擎按 DAG 编排节点，协调 RPA、人工、系统调用
- VarStore 统一变量空间，节点间数据自动流转
- 表单驱动交互，选择任务 → 填参数 → 一键执行

**关于 AI 的定位**：
- MVP 不包含 AI 编排能力，流程由开发者用 YAML 定义
- AI 作为未来能力，按需接入（如竞品分析、报告生成）
- 这与 MRD 的"开箱即用"定位一致：给用户成品，不让用户搭积木

### 1.2 核心目标

| 目标 | 描述 |
|------|------|
| 提效 | 自动化重复的跨系统操作任务 |
| 编排 | YAML 定义流程，引擎自动编排执行 |
| 沉淀 | 流程模板可复用，SOP 可传承 |
| 开箱即用 | 用户无需编程，选择模板即可使用 |

### 1.3 MVP 验证目标与结果

| 目标 | 状态 | 说明 |
|------|------|------|
| 验证框架 | 已完成 | YAML 流程 → DAG 执行 → 状态流转 → VarStore 变量传递 全链路跑通 |
| 验证场景 | 已完成 | 开票流程（RPA + 人工录入 + RPA）三节点场景落地 |
| 验证跨系统 | 已完成 | 影刀 RPA（文件协议 + HTTP 回调）+ 人工确认 协作验证通过 |
| 自用验证 | 进行中 | 开票流程已可实际使用 |

### 4.2 核心机制

#### 4.2.1 YAML 流程定义

流程由开发者编写 YAML，定义 DAG 结构：

```yaml
id: invoice-process
name: 给买家开票

parameters:          # 用户表单输入
  - key: excelPath
    type: string
    input: file

variables:           # 运行时变量（带默认值）
  - key: orderList
    type: array

nodes:               # 执行节点 DAG
  - id: send_invoice_list
    type: rpa
    inputs:
      excelPath: "{{ excelPath }}"     # {{ key }} = 地址引用
    outputs:
      orderList: []

  - id: input_invoice
    type: manual
    config:
      fields:                           # 人工节点可定义表单字段
        - key: invoiceFiles
          type: file
          multiple: true
    outputs:
      - invoiceFiles

connections:         # DAG 路由
  start: send_invoice_list
  send_invoice_list:
    success: input_invoice
```

**设计要点**：
- `{{ key }}` 是地址引用，不是值 — 运行时从 VarStore 解析
- `outputs` 定义写回 VarStore 的变量名
- `connections` 声明式路由，支持 success/error 分支
- `config.fields` 让人工节点支持动态表单（文件上传等）

#### 4.2.2 任务状态流转

**任务实例状态**：

| 状态 | 说明 |
|------|------|
| pending | 待执行 |
| running | 执行中（节点正在运行） |
| waiting | 等待外部（RPA 回调 / 人工确认） |
| completed | 已完成 |
| failed | 失败 |

**状态流转**：
```
pending → running → completed
              ↓
           waiting → (RPA回调/人工确认) → running
              ↓
           failed → (retry) → running
```

#### 4.2.3 节点类型

| 类型 | 执行方式 | 返回 | 说明 |
|------|----------|------|------|
| rpa | 写 JSON 文件 → 影刀轮询执行 → HTTP 回调 | Waiting → Result | 异步 |
| manual | 前端推送等待状态 → 用户操作 → 回调 | Waiting → Result | 异步 |
| system | 直接调用本地函数 | Result | 同步 |
| feishu_notify | 发送飞书机器人消息 | Result | 同步 |
| feishu_read | 读取飞书多维表格 | Result | 同步（TODO） |
| feishu_write | 写入飞书多维表格 | Result | 同步（TODO） |

#### 4.2.4 VarStore（变量系统）

VarStore 是系统的"内存总线"，提供统一的变量读写接口：

```
Load 阶段: parameters默认值 + variables默认值 + 用户输入 → 打平一层 → VarStore
寻址阶段: {{ key }} → VarStore.get_all() → 解析为真实值
写回阶段: 节点 outputs → VarStore.bulk_set() → 持久化到 DB
释放阶段: 任务完成 → VarStore.clear() → 释放内存缓存
```

**持久化策略**：内存缓存（热路径） + SQLite 写穿（持久化） + 懒加载（冷启动恢复）

#### 4.2.5 RPA 协作架构

**核心原则：步骤原子化 + 状态外置**

影刀 RPA 是同步执行的，无法在执行中暂停。因此：
- 每个 RPA 步骤独立执行，执行完即结束
- 上下文保存在 VarStore（不依赖 RPA 内存）
- 由 TaskHandler 决定下一步执行什么

**通信协议**：
```
Backend → RPA:  文件系统 (JSON 文件轮询)
RPA → Backend:  HTTP POST (回调 URL)
```

### 4.3 核心流程

#### 4.3.1 创建并执行任务

```
用户选择任务类型 → 填参数表单 → 点击执行
        ↓
POST /api/tasks → handlers.on_task_trigger()
        ↓
TaskHandler.trigger()
  ├─ 合并 variables默认值 + parameters默认值 + 用户输入
  ├─ INSERT tasks 记录
  ├─ VarStore.load() 写入统一变量空间
  ├─ 记录 TriggerEvent
  └─ _run_node(start_node) → 开始 DAG 执行
```

#### 4.3.2 DAG 执行循环

```
_run_node(node):
  ├─ 创建 TaskNode 记录
  ├─ ① 寻址: _prepare_params() → {{ key }} → VarStore 取值
  ├─ ② 调用: executor.execute(params)
  │     ├─ Result (同步完成)
  │     │   ├─ ③ 写回: _save_node_outputs() → VarStore
  │     │   └─ _get_next_node() → _run_node(next) 递归
  │     └─ Waiting (异步等待)
  │         └─ 任务挂起 → 等待回调
  └─ 无后续节点 → task COMPLETED
```

#### 4.3.3 回调恢复

```
外部回调 (RPA完成 / 用户确认)
  ├─ POST /callback/rpa/{unit_id}
  └─ POST /callback/human/{task_id}
        ↓
TaskHandler.resume()
  ├─ 加载上下文（VarStore 懒加载）
  ├─ executor.parse(data) → Result
  ├─ _save_node_outputs() → VarStore
  ├─ 更新节点状态
  └─ _get_next_node() → _run_node(next)
```

#### 4.3.4 开票流程（实际场景）

```
用户: 选择「开票」→ 填写 Excel 路径 → 执行
        ↓
VarStore: { excelPath: "D:/开票.xlsx", orderList: [], ... }
        ↓
节点1 (RPA): 整理 Excel
  inputs:  excelPath ← VarStore
  outputs: orderList → VarStore
        ↓
节点2 (Manual): 录入发票
  config.fields: [{ key: invoiceFiles, type: file, multiple: true }]
  outputs: invoiceFiles → VarStore
        ↓
节点3 (RPA): 录入系统
  inputs:  invoiceFiles ← VarStore
  outputs: orderList → VarStore
        ↓
Task COMPLETED, VarStore.clear()
```

## 6. 优化回路

### 6.1 问题回收机制

| 问题类型 | 发现方式 | 记录位置 |
|----------|----------|----------|
| 节点执行失败 | 执行引擎捕获 + 前端状态展示 | task_nodes.error + events 表 |
| RPA 回调超时 | watchdog 定时检测 | 任务标记 failed |
| 变量传递异常 | 前端 VarStore 面板检查 | task.context |

### 6.2 问题归因

```
问题发生
    ↓
判断问题类型
    ├── RPA 执行失败 → 检查影刀脚本 / 目标网站变化
    ├── 变量寻址失败 → 检查 YAML outputs/inputs 定义
    ├── 回调超时 → 检查影刀进程 / 网络连通性
    └── 前端展示异常 → 检查 WebSocket / API 返回
```

### 6.3 闭环修复

| 问题类型 | 修复方式 |
|----------|----------|
| RPA 脚本 Bug | 修复影刀脚本，重试任务 |
| YAML 定义错误 | 修改 YAML + 热重载 (`POST /api/flows/reload`) |
| 框架层 Bug | 修复代码，重启服务 |

### 7.2 交互原则

| 场景 | 灵活度 | 交互方式 |
|------|--------|----------|
| 选择任务类型 | 低 | 侧边栏点击 |
| 配置参数 | 低 | 表单填写（支持文件选择） |
| 执行任务 | 低 | 按钮点击 |
| 人工确认节点 | 低 | 确认/取消按钮 |
| 人工录入节点 | 中 | 动态表单（config.fields 驱动） |
| 查看执行状态 | 低 | 节点时间线 + IO 面板 |
| 查看变量 | 低 | VarStore 面板 |
| 调度配置 | 中 | Cron 弹窗表单 |

### 7.3 人工节点表单

当 YAML 节点定义了 `config.fields` 时，前端自动渲染表单：

| 字段类型 | 渲染方式 | 说明 |
|----------|----------|------|
| file | 文件路径输入框（多行支持） | 支持 accept 过滤、multiple 多选 |
| text | 文本输入框 | 通用文本 |
| number | 数字输入框 | 带验证 |

无 `config.fields` 时，只显示确认/取消按钮。

```
│ processed_at TEXT       │
└─────────────────────────┘
```

### 8.2 字段语义

| 字段 | 语义 |
|------|------|
| tasks.parameters | 仅用户原始表单输入（供审计/重跑） |
| tasks.context | VarStore 的完整快照（打平的所有变量） |
| task_nodes.input_params | 节点执行时解析后的实际参数 |
| task_nodes.output_result | 执行器返回的完整 result.data |

### 8.3 流程定义存储

流程定义不在数据库中，而是存储为 YAML 文件：
- 位置：`backend/flows/definitions/*.yaml`
- 加载：启动时 FlowRegistry 扫描加载
- 热重载：`POST /api/flows/reload`

## 9. 异常与兜底

### 9.1 异常场景

| 场景 | 处理策略 | 实现状态 |
|------|----------|----------|
| RPA 执行失败 | 回调返回 error，节点标记 failed | 已实现 |
| RPA 回调超时 | watchdog 定时检测，超时标记 failed | 已实现（默认 10 分钟） |
| 人工取消操作 | 节点标记 cancelled/failed，任务停止 | 已实现 |
| 变量寻址失败 | {{ key }} 找不到值时保留原始表达式 | 已实现 |
| 服务器重启 | VarStore 懒加载从 DB 恢复 | 已实现 |

### 9.2 兜底机制

| 机制 | 说明 | 实现状态 |
|------|------|----------|
| 事件日志 | 完整记录 trigger/resume 事件 | 已实现 |
| 节点执行日志 | 记录每步 input/output | 已实现 |
| 任务重试 | 从当前节点重新执行 | 已实现 |
| 软删除 | 删除不丢历史数据 | 已实现 |
| VarStore 面板 | 前端可查看所有运行时变量 | 已实现 |
